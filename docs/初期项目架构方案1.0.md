### 核心模块职责说明

1. **API****层**：只做路由分发、参数校验、权限校验，不写业务逻辑，所有业务下沉到services层。
2. **Agent层**：完全独立，只通过工具与外部交互，不直接操作数据库、不直接调用接口，保证Agent逻辑可复用、可测试。
3. **RAG层**：封装所有向量相关操作，向上只提供「入库」和「检索」两个核心能力，切换向量库无需修改上层代码。
4. **DB层**：ORM模型与CRUD分离，业务代码不直接写SQL，保证数据操作规范。
5. **Services层**：业务编排层，比如生成膳食方案时，负责调用Agent、保存结果、返回前端，串联全流程。

## 七、架构设计原则（面试可直接说）

1. **分层解耦**：API层、业务层、Agent层、数据层严格分离，任意模块替换不影响其他层（比如换大模型、换向量库无需改业务代码）。
2. **配置与代码分离**：所有密钥、环境参数全部通过环境变量注入，不硬编码在代码中。
3. **面向接口编程**：向量库、大模型、记忆模块都做抽象封装，上层依赖抽象而非具体实现，兼容多种技术选型。
4. **工程化规范**：统一异常处理、统一日志格式、统一数据校验，符合工业级后端服务开发标准。

## 各模块核心功能拆解（项目简历亮点）

### 1. 前端交互层（核心页面）

1. 用户档案录入：身高、体重、年龄、性别、慢性疾病（糖尿病/痛风/高血压等）、食物忌口、口味偏好（辣/清淡/甜）、所在城市地域、饮食禁忌（宗教/过敏）；
2. AI对话界面：自然语言提问，如“给我设计3天减脂餐”“痛风患者一日三餐搭配”；
3. 膳食计划展示：早中晚三餐+加餐，食材用量、烹饪方式、热量、营养成分、养生小贴士；
4. 知识库管理：上传营养学、中医膳食养生文档，后台查看向量库状态；
5. 历史记录：保存过往膳食方案，支持重新生成、修改。

### 2. FastAPI网关层

- 用户注册、登录、JWT鉴权；
- 统一接口：用户管理接口、Agent对话接口、知识库CRUD接口、食谱导出接口；
- 全局异常捕获、请求日志、接口限流，区分开发/生产环境配置。

### 3. LangGraph 膳食规划Agent（项目核心创新点，面试重点）

采用**多步骤循环Agent架构**，解决单一LLM生成食谱不精准、忽略用户身体条件的问题，执行流程闭环：

1. **信息收集节点**：判断当前用户是否完善身体、忌口、地域信息，缺失则主动追问用户；
2. **知识库检索节点**：根据用户需求（减脂/养胃/控糖/日常养生）构造检索词，调用Milvus检索对应营养学、膳食禁忌知识；
3. **约束校验节点**：读取用户慢病、忌口规则，过滤知识库中冲突食材；
4. **地域适配节点**：结合地域饮食特点（南方清淡、北方面食、沿海海鲜适配等）调整食材；
5. **食谱生成节点**：综合所有信息，LLM输出结构化膳食方案（早/中/晚/热量/营养）；
6. **校验修正节点**：二次检查食谱是否存在忌口、不适合慢病食材，存在则重新生成；
7. **结果输出节点**：整理膳食方案+配套健康养生建议，存入数据库返回前端。

### 4. RAG知识库层（保证专业度，避免大模型幻觉）

知识库文档分类（体现项目完备性）：

1. 现代营养学：减脂、控糖、控尿酸、三高人群饮食指南、每日营养素摄入标准；
2. 中医膳食养生：四季养生、体质（阴虚/阳虚/湿热）对应饮食禁忌；
3. 地域特色饮食：南北菜系、各地家常健康食谱；
4. 食物禁忌库：食材相克、过敏食材、慢性病禁食清单；
5. 食材营养数据库：各类食材热量、蛋白质、碳水、GI值。

流程：文档上传 → 文本清洗分割 → BGE向量化 → 存入向量库 → Agent检索召回Top5相关文档作为LLM上下文。

### 5. 数据持久层

1. PostgreSQL表设计（核心三张表）
   1. user：用户基础身体、地域、忌口、口味数据；
   2. diet_record：生成的每日/每周膳食方案；
   3. chat_memory：用户对话记录；
2. Redis：缓存用户实时对话上下文，避免每次请求查询数据库；缓存高频检索向量，提升检索速度。

# 四、关键开发指导与避坑建议（求职项目提分关键点）

## 1. Agent核心加分设计（区别于普通RAG Demo）

不要只做简单问答RAG，一定要突出**Agent自主规划、工具调用、自我修正**：

- 当用户未填写糖尿病、过敏等信息时，Agent主动打断生成，引导用户补充；
- 生成食谱后自动校验，若出现用户忌口食材，自动重新检索知识库二次生成；
- 支持批量生成7天不重复膳食方案，自动搭配每日不同食材保证营养均衡。

## 2. RAG优化细节（面试高频提问点）

- 使用中文专用嵌入模型bge-large-zh，比openai embedding中文效果更好；
- 文本分块采用语义分块而非固定长度，保证营养学知识完整性；
- 检索增加重排（CrossEncoder），提升知识库召回精准度，减少无关养生内容。

## 3. 求职项目避坑

1. 不要只做后端无前端：面试官会认为只是Demo，缺乏完整落地思维；
2. 不要只用单一LLM：代码兼容多家大模型API，体现工程通用性；
3. 不要无持久化：所有用户数据、对话、食谱必须存入数据库，不能内存临时存储；
4. 必须容器化部署：Docker Compose是工业落地标准，大幅提升项目含金量；
5. 知识库不能太少：至少50份以上营养学、中医膳食文档，体现RAG真实价值。

## 4. 拓展功能（可选，进一步提升竞争力）

1. 食材热量自动计算，输出每日摄入热量统计；
2. 四季养生自动适配，根据当前季节调整膳食；
3. 食材替换功能：用户不喜欢某食材，Agent自动替换同类营养食材；
4. 膳食导出PDF功能；
5. 用户食谱收藏、打分功能。
