## 七、面试官高频追问 & 参考答案（**务必提前准备**）

### Q1：为什么用 LCEL，不直接用 LangGraph / 手写函数？
> **答**：三方面权衡。① LangChain 社区更大，LCEL 是现在主流考法；② 我的链路是严格线性 6 步，不需要复杂的条件分支和循环，LCEL 表达力足够；③ LCEL 自带 `.stream()` `.batch()` 等一等公民能力，做 SSE 流式更顺手。**但** 在架构上预留了切换 LangGraph 的接口（所有 tool 输出都是 dict，不耦合 LCEL 语法糖），未来如果加了"医生二次审核"这种分支节点会迁移。

### Q2：你是怎么降低营养幻觉的？（**必考**）
> **答**：3 层防线。① **检索层**：用户问题先过 RAG，只从营养学权威文档 Top-K 片段里取营养数据；② **工具层**：RAG 结果不直接塞 Prompt，而是包装成 `rag_tool(query)`，LLM 需要数据才调，减少无关 Context；③ **校验层**：生成完的方案再过 `validate_tool`——糖尿病就查有没有蜂蜜/白粥等高 GI 食材，过敏原做 exact match，不合法自动调用 revise prompt 二次生成。

### Q3：RAG 的中文嵌入为什么选 bge-small-zh-v1.5？
> **答**：在自建中文营养问答评测集上跑过：bge-small-zh-v1.5 的 Top-3 命中率 86%，单条 ~320ms，512 维；本地部署零成本，演示现场不容易翻车。向量库选 Chroma 同理，本地零配置 + 纯 Python，生产可以平滑切 Qdrant / Milvus。

### Q4：7 天食谱 JSON 解析失败 / NoneType 崩溃这个坑，你怎么解决的？（**必考，真实踩坑**）
> **答**：经典坑。7 天食谱 JSON 很长（3000~8000 字符），LLM 经常出现四种"脏"返回：① 外面包 ```json 代码块；② JSON 后面跟自然语言尾巴；③ 末尾缺 `]}` 被截断；④ 直接返回 None。原来 `JsonOutputParser` 一失败，`diet_plan` 就是 None，后续 `diet_plan.get('total_calories')` 直接 `'NoneType' object has no attribute 'get'` 崩溃。我做了三级兜底：第一层剥离 ```` ```json ```` 代码块再解析；第二层用 `JSONDecoder.raw_decode` 从第一个 `{` 开始解析，遇到合法 JSON 结尾就截断（忽略自然语言尾巴）；第三层统计 `{`/`}` 和 `[`/`]` 的数量差，自动补齐缺失的括号。解析完再过 `_sanitize_diet_plan` 做结构标准化，保证所有关键 key 都有默认值。改完解析成功率从 72% → 98%，NoneType 崩溃彻底消失。

### Q5：7 天食谱生成经常超时失败，怎么排查的？
> **答**：看日志发现 DeepSeek 每次都返回 200 OK（说明服务端能生成完），但客户端每 30 秒触发一次 `Retrying request to /chat/completions`，重试 3 次后报 `Request timed out`。根因是 `ChatOpenAI` 默认 `timeout=30s`，而 7 天长 JSON 实际要 60~120s 生成。把 `timeout` 调到 180s、`max_tokens` 从 4096 调到 8192 后，7 天方案生成成功率 100%。

### Q6：用户多轮对话里提到"我不想吃鸡蛋"，系统是怎么记住并避开的？
> **答**：两层记忆。① **短期 Redis 会话记忆**：按 session_id 存最近 N 轮消息，每次生成拼入对话历史（防止上下文爆炸）；② **长期持久化忌口**：健康档案里有 `food_taboo` 字段，每次生成前 `user_tool` 从 `user_profile` 注入，`validate_tool` 校验时会同时检查会话内临时忌口和长期忌口。无 Redis 时自动降级内存存储。

### Q7：SSE 流式打字机效果是怎么实现的？
> **答**：FastAPI 用 `StreamingResponse(media_type="text/event-stream")`，分两类事件：① 6 阶段进度事件（collect_info/retrieve_knowledge 等，每个环节 start/complete 各推一次）；② 最终答复用 `_stream_text_chunks` 把摘要文本切成 2~5 字的小 chunk，逐段 yield 形成"打字机"效果，不增加额外 LLM 调用。前端用 `fetch` + `ReadableStream.getReader()` 读取，按 `data:` 解析 SSE，首块到达时清掉阶段提示，后续 chunk 直接 `aiMsg.content += chunk` 实时追加。

### Q8：chronic_disease 字段存成 "[]" 字符串被拼进检索 query 的 bug 怎么修的？
> **答**：用户档案的 `chronic_disease` 可能存成 `"[]"`（空列表字符串）、`"['糖尿病']"`（repr）、`'["高血压"]'`（JSON）等多种格式。原来直接 `f"{chronic}饮食 {query}"` 拼接，会把字面量 `[]` 拼成 `"[]饮食 给我一周减脂食谱"` 污染检索。我写了 `_normalize_chronic_disease` 统一解析：先试 JSON 再试 `ast.literal_eval`，解析成列表取第一个有意义的元素，"[]"/None/"" 都返回空串，检索 query 干净了。

### Q9：如果用户量大了，你会先优化哪里？
> **答**：按优先级。① RAG 检索 Redis LRU 缓存；② LLM 请求异步化 + worker 池并发；③ Chroma 单机换 Qdrant/Milvus 分布式；④ 方案去重（user_profile hash + query 语义 hash 复用结果）；⑤ MySQL 连接池调优。
