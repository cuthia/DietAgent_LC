## 一、改进 1：LLM Dynamic Planning（动态规划层）—— 从"只会出食谱"到"膳食健康全科助手"

### 1.1 现状问题

现在的代码 [chain.py](file:///e:/Programs/Python%20Programs/DietAgent_LC/backend/app/agent/chain.py) 无论用户问什么（"我每天吃 4 个鸡蛋多不多？"、"糖尿病能吃南瓜吗？"、"帮我算下 BMI"、"今天好热吃什么？"），**都会硬跑 6 步完整流程**：

```
信息收集 → 知识检索 → 约束构建 → 生成完整 JSON 食谱 → 合规校验 → 格式化
```

问题：
- **成本浪费**：简单 QA 不需要调用 RAG、不需要 LLM 输出 8000 token 的 JSON；
- **答非所问**：用户问"鸡蛋多不多"，输出却是一份完整三餐食谱，用户体验差；
- **面试硬伤**：Planning 层完全硬编码，无法证明"LLM 动态决策"能力。

### 1.2 目标能力矩阵（营养助手不止出食谱）

| Intent（意图枚举） | 用户 Query 示例 | 执行路径 | 核心工具 |
|---|---|---|---|
| `diet_plan`（生成食谱） | "一周减脂食谱"、"今天吃什么"、"三日控糖" | 完整 6 步链路（原流程） | `rag_search`、`validate_tool`、`region_tool`、**天气工具** |
| `nutrition_qa`（营养问答） | "每天吃 4 个鸡蛋多不多？"、"南瓜的升糖指数" | Planner → QA Prompt + RAG（可选）→ 直接回答 | `rag_search`（可选） |
| `health_calc`（健康计算） | "我 BMI 多少？"、"基础代谢率"、"每天需要多少蛋白质" | Planner → 计算器工具（纯数学，不用 LLM）→ 结果解释 | `bmi_calc_tool`、`bmr_calc_tool`、`protein_target_tool` |
| `food_eval`（食材评估） | "痛风能吃豆腐吗？"、"高血压能喝牛奶吗？" | Planner → RAG 精准检索 → 合规判断 → 结论 + 摄入量建议 | `rag_search`、`food_taboo_tool` |
| `profile_update`（档案修正） | "哦对了我海鲜过敏"、"我改成糖尿病了" | Planner → 提取修正字段 → `update_user_info` → 确认 | `user_update_tool` |
| `casual_chat`（闲聊/致谢） | "谢谢"、"你好" | Planner → 直接礼貌回答 | （无工具） |
| `info_collection`（档案引导） | （用户档案缺失时触发） | 追问缺失字段（现有 step_collect_info 逻辑保留） | `get_user_info` |

### 1.3 实现方案：新增 step_0 `step_plan_execution`

#### 1.3.1 新增文件：`backend/app/agent/prompts/planner_prompt.py`

**LLM Planner Prompt** 让模型输出结构化 JSON 决策（注意使用 `{{ }}` 转义花括号，避免 ChatPromptTemplate 误解析）：

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser
from pydantic import BaseModel, Field
from typing import List, Optional

class ExecutionPlan(BaseModel):
    intent: str = Field(description="意图枚举，必须是 diet_plan/nutrition_qa/health_calc/food_eval/profile_update/casual_chat/info_collection 之一")
    plan_days: int = Field(description="仅 diet_plan 意图有效：1/2/3/5/7")
    need_rag: bool = Field(description="是否需要检索知识库")
    rag_query_hint: Optional[str] = Field(description="RAG 检索关键词建议（need_rag=true 时必填）")
    need_weather: bool = Field(description="是否需要结合当地天气决策（生成食谱、消暑/保暖建议时为 true）")
    need_calc_tools: List[str] = Field(description="健康计算器工具名列表：bmi / bmr / protein_target，仅 health_calc 意图使用")
    profile_updates: Optional[dict] = Field(description="profile_update 意图：要更新的 {字段: 值}")
    tools_to_call: List[str] = Field(description="显式声明此轮要调用的工具名列表（Function Calling 模式下会并行调用）")
    reasoning: str = Field(description="决策推理过程：为什么选择这个 intent + 这些工具")

PLANNER_PROMPT = ChatPromptTemplate.from_messages([
    ("system", """你是膳食健康助手的 Planner（规划器）。根据用户 Query + 用户档案，**在执行前**先判断用户的真实意图，并决策后续要调用哪些工具与执行链路。

## 意图与决策规则
1. **diet_plan**：用户明确要食谱/餐单/饮食方案（包含"食谱、餐单、吃什么、方案、减脂餐、控糖餐、一周、一天"等关键词）。
   - 天数识别："一周/7天/七天"→7；"三天/3天"→3；"两天/2天"→2；"五天/工作日"→5；只说"一份/今天/一天/今日"→1。
   - need_rag=true，rag_query_hint=慢病名+饮食+用户目标；need_weather=true（热天自动推荐消暑、冷天推荐暖身）。

2. **nutrition_qa**：询问营养成分、饮食原则、食物功效（含"蛋白质、热量、卡路里、升糖指数、GI、能不能吃、有没有营养、怎么吃更好"）。
   - need_rag=true（回答必须基于知识库），rag_query_hint=食材名+问题词。

3. **health_calc**：明确请求计算 BMI / BMR（基础代谢）/ 每日蛋白质目标 / 每日热量目标。
   - need_rag=false；need_calc_tools 填工具名列表；如果缺少身高/体重/年龄/性别 → **先改 intent=info_collection** 让 Planner 触发追问，不要瞎算。

4. **food_eval**：询问某食材"能不能吃、好不好、会不会痛风/升糖/过敏"（与 nutrition_qa 区别：针对用户个人忌口/慢病做合规判断，而非通用知识）。
   - need_rag=true，rag_query_hint=食材+慢病/忌口；tools_to_call=["food_taboo_check_tool"]。

5. **profile_update**：用户在对话中补充/修正档案（"哦我海鲜过敏"、"我是糖尿病"、"我 175cm/70kg"）。
   - 识别字段 → 填入 profile_updates dict（字段名必须与 user_profile schema 一致：age/gender/height/weight/chronic_disease/food_taboo/region/diet_goal/taste_preference）。
   - tools_to_call=["user_profile_update_tool"]

6. **casual_chat**：问候/致谢/闲聊（"你好"、"谢谢"、"再见"）。
   - need_rag=false，所有工具标志 false。

7. **info_collection**：当用户 age/gender/height/weight 任一核心字段缺失，且用户意图是 diet_plan / health_calc / food_eval（需要个人数据的意图），则**强制把 intent 改回 info_collection**，优先追问完善档案。
   - 注：nutrition_qa / casual_chat 不强制补档案（用户只想问南瓜的 GI 不应被强制问身高）。

## 输出格式（严格 JSON，禁止额外文字）：
{{json_schema}}

## 重要提醒
- **同一个 Query 通常只匹配一个 intent**，禁止多意图。
- 决策时必须同时考虑"用户档案是否足够支撑该意图的执行"，不够就降级 info_collection。
- reasoning 字段必须写中文推理过程，面试调试 / 日志排查 / 前端"规划思路"展示都会用到它。"""),

    ("human", """## 用户 Query
{user_query}

## 已有对话历史（最近 6 轮，用于识别上下文指代，如用户说"我是 175/70"实际是 profile_update）
{recent_history}

## 用户当前档案（空字段 = 缺失）
{user_profile_snapshot}

请输出规划 JSON。""")
]).partial(json_schema=ExecutionPlan.model_json_schema())  # 用 Pydantic 精确 schema
```

#### 1.3.4 新增工具分析：哪些功能该封装成 `@tool`（LangChain 工具）

> **核心判断原则**：纯数学/确定性逻辑 → 必须工具化（省钱 + 精确）；需要 LLM 基于外部知识推理 → 走 RAG + LLM。

| 工具名 | 类型 | 是否 @tool | 实现位置 | 说明 |
|---|---|---|---|---|
| `bmi_calc_tool(height_cm, weight_kg)` | 确定性计算 | ✅ 是 | `tools/health_calc_tool.py` 新增 | `bmi = weight_kg / (height_m)^2`，返回 {bmi, category:"偏瘦/正常/超重/肥胖"} + 中文解读区间。**必须工具化**：LLM 算 BMI 会算错，纯数学不花 token。 |
| `bmr_calc_tool(age, gender, height_cm, weight_kg)` | 确定性计算 | ✅ 是 | 同上 | 用 Mifflin-St Jeor 公式：男 BMR=10w+6.25h-5a+5；女 BMR=10w+6.25h-5a-161。**必须工具化**：LLM 代不出公式+会算错数。 |
| `protein_target_tool(weight_kg, diet_goal)` | 规则计算 | ✅ 是 | 同上 | 普通 0.8~1g/kg；减脂 1.6~2g/kg；增肌 1.6~2.2g/kg。 |
| `food_taboo_check_tool(food_name, chronic_disease, food_taboo)` | 规则 + 知识库匹配 | ✅ 是 | `tools/validate_tool.py` 扩展 | 原 validate_tool 有食物禁忌判断逻辑，抽成独立 `@tool` 供 food_eval 意图单独调用。 |
| `user_profile_update_tool(user_id, updates_dict)` | 写库操作 | ✅ 是 | `tools/user_tool.py` 扩展 | 把现有 `update_user_info` 包成 LangChain `@tool`（**加白名单字段校验**：只允许 age/gender/height/weight/chronic_disease/food_taboo/region/diet_goal/taste_preference 被改，防止 Prompt 注入）。 |
| `weather_tool(region_name, user_ip)` | HTTP API（高德） | ✅ 是 | `tools/weather_tool.py` 新增 | 改进 4 专用，见第 4 节。 |
| `rag_search_tool(query, category)` | 向量检索 | ✅ 是 | `tools/rag_tool.py` 扩展 | 现有 `search_knowledge` 包 `@tool`。Function Calling 模式下由 LLM 主动调。 |
| `region_adapt_tool(region_name)` | 本地映射表 | ✅ 是 | `tools/region_tool.py` 扩展 | 现有 `get_region_diet_features` 包 `@tool`。 |

**不需要工具化的（直接用 LLM + Prompt 搞定）**：
- 营养知识问答内容生成 → 把 RAG 结果塞进 Prompt 让 LLM 组织语言；
- 闲聊回复 → 2~3 句礼貌语，不需要工具；
- 完整膳食方案生成 → 仍然走 `DIET_GENERATE_PROMPT | self.llm`（因为 JSON Schema 太复杂，`bind_tools` 让 LLM 返回结构化 JSON 不如专用 Prompt 稳）。

## 二、改进 2：LangChain Function Calling（bind_tools）——标准 ReAct/Observation 闭环

### 2.1 目标

把上一节确认需要工具化的 6 个工具（bmi/bmr/protein/food_taboo/profile_update/weather/rag/region_adapt）统一注册给 LLM，形成真正的：

```
LLM 思考 → 选择工具 & 填参 → 执行工具（Observation）→ LLM 基于 Observation 生成结论
```

这是面试中"标准 Agent 流程"的硬核证据。

### 2.2 实现方案

#### 2.2.1 `DietAgentChain.__init__` 新增工具注册链

```python
from langchain_core.tools import tool
# 改造后的 tool 文件中每个函数都装饰了 @tool，直接 import 实例
from agent.tools.health_calc_tool import bmi_calc_tool, bmr_calc_tool, protein_target_tool
from agent.tools.validate_tool import food_taboo_check_tool
from agent.tools.user_tool import user_profile_update_tool
from agent.tools.weather_tool import weather_tool          # 改进4
from agent.tools.rag_tool import rag_search_tool
from agent.tools.region_tool import region_adapt_tool

# 工具注册表（所有工具统一放这里）
self.ALL_TOOLS = [
    bmi_calc_tool, bmr_calc_tool, protein_target_tool,
    food_taboo_check_tool, user_profile_update_tool,
    weather_tool, rag_search_tool, region_adapt_tool,
]

# 给 LLM 绑定工具（ChatOpenAI.bind_tools → 底层转成 function_call / tools JSON Schema）
self.llm_with_tools = self.llm.bind_tools(self.ALL_TOOLS)

# 工具调用辅助：RunnableLambda 包一层，专门处理 tool_calls
from langchain_core.runnables import RunnableLambda

self.tool_executor = RunnableLambda(self._execute_tool_calls)
```

#### 2.2.2 新增 `_execute_tool_calls` 统一工具执行器

```python
from langchain_core.messages import ToolMessage

async def _execute_tool_calls(self, ai_msg):
    """
    输入：上一轮 LLM 返回的 AIMessage（可能含 .tool_calls）
    输出：ToolMessage 列表（含每个工具的真实结果）
    支持并行工具调用（多个 tool_calls 并发 await）
    """
    if not hasattr(ai_msg, "tool_calls") or not ai_msg.tool_calls:
        return []

    tool_map = {t.name: t for t in self.ALL_TOOLS}
    tasks = []
    for tc in ai_msg.tool_calls:
        t = tool_map.get(tc["name"])
        if t is None:
            obs = f"错误：未找到工具 {tc['name']}"
        else:
            # ainvoke 调用 LangChain @tool 的标准 LCEL 接口
            obs = await t.ainvoke(tc.get("args") or {})
        tasks.append(ToolMessage(
            content=str(obs) if not isinstance(obs, str) else obs,
            tool_call_id=tc["id"],
            name=tc["name"],
        ))
    return tasks  # ToolMessage[] 喂回 LLM 形成 ReAct 闭环
```

#### 2.2.3 在 `nutrition_qa` / `food_eval` / `health_calc` 三个路由分支中使用 ReAct 模式

示例（`nutrition_qa` 分支，伪代码）：
```python
async def step_food_eval_reply(self, input_data):
    # 1. 把上下文 + 用户问题拼成初始 message 列表（System + Human）
    messages = build_initial_messages(input_data)

    # 2. LLM_WITH_TOOLS 第一轮：决定要不要调 rag / food_taboo
    ai1 = await self.llm_with_tools.ainvoke(messages)
    messages.append(ai1)

    # 3. 如果 LLM 决定调工具 → 并发执行 → ToolMessage 追加回去
    if ai1.tool_calls:
        obs = await self.tool_executor.ainvoke(ai1)
        messages.extend(obs)
        # 4. LLM 第二轮：拿到真实观察后生成结论
        ai2 = await self.llm_with_tools.ainvoke(messages)
        messages.append(ai2)

    # 5. 取最后一条 AIMessage 作为 reply
    reply = messages[-1].content
    return { "success": True, "need_info": False, "diet_plan": None, "message": reply }
```

> **关键设计决策（面试必答点）**：diet_plan 分支**不**用 Function Calling 生成食谱 JSON。原因是：
> 1. 食谱 JSON Schema 字段极多（嵌套 5 层，days 数组 7 元素），`bind_tools` 的 function_call 模式下 LLM 经常漏填 days 元素、breakfast.items 缺字段，调试成本远高于专用 Prompt；
> 2. 食谱生成需要**强约束（食材种类数、热量分配比例、不重复率）**，这些约束在专用 `DIET_GENERATE_PROMPT` 中写成 System Prompt 段落，比写进 function description 更稳定；
> 3. 但 `validate_diet_plan` / `revise` 环节仍然是**显式工具调用式的 Observation 闭环**——我们是"对需要最强确定性的节点用专用 Chain，其余节点走标准 Agent ReAct"，这是生产级 Agent 的正常工程化取舍，不是不会写 Function Calling。

## 三、改进 3：混合 LCEL 编排（消除无用 import + 对外 Runnable 协议统一）

### 3.1 现状瑕疵

- [chain.py:22](file:///e:/Programs/Python%20Programs/DietAgent_LC/backend/app/agent/chain.py#L22) `RunnableLambda / RunnablePassthrough` **import 了但 974 行代码全文件没使用**——这是面试扣分点（"设计意图和实现不一致"）；

```python
# ---------- 真正的 LCEL sub-chain（线性段用 |，消除 import 无用的尴尬） ----------
# 子链A：diet_plan 意图的线性 4 连段（检索→约束→天气→生成）
self.diet_linear_chain = (
    self.r_retrieve
    | self.r_build_constraints
    | self.r_fetch_weather
    | self.r_generate_diet
)
# 子链B：nutrition_qa 意图（条件检索→校验→答复，答复内部是 llm_with_tools ReAct 链）
self.nutrition_qa_chain = (
    self.r_retrieve_cond
    | RunnableLambda(self.step_nutrition_qa_answer)
)
# 子链C：food_eval（检索→禁忌判断→ReAct 答复）
self.food_eval_chain = (
    self.r_retrieve_cond
    | RunnableLambda(self.step_food_taboo_check)
    | RunnableLambda(self.step_food_eval_reply)
)
```

然后把 `process()` 中原先的顺序 await：
```python
input_data = await self.step_retrieve_knowledge(input_data)
input_data = await self.step_build_constraints(input_data)
input_data = await self.step_generate_diet(input_data)
```
改成：
```python
input_data = await self.diet_linear_chain.ainvoke(input_data)
```

#### 3.2.2 对外暴露顶级 Runnable：`self.as_runnable()`

```python
def as_runnable(self) -> RunnableLambda:
    """
    把 DietAgentChain 对外暴露成一个标准的 LangChain Runnable：
    - 输入：{ "user_id": int, "user_query": str }
    - 输出：process() 返回的标准 result dict
    - 支持的标准接口：ainvoke / astream / abatch / with_fallbacks / with_config(callbacks=[LangSmithTracer])
    """
    async def _run(input_dict):
        return await self.process(
            user_id=input_dict["user_id"],
            user_query=input_dict["user_query"],
        )
    return RunnableLambda(_run).with_config(
        run_name="DietAgentChain",
        tags=["DietAgent", "Production"],
    )
```

### 3.3 改动总结（面试对比表）

| 点 | 改前 | 改后 |
|---|---|---|
| `RunnableLambda` import | 无用（扣分点） | 每个 step 一个实例 + 子链用 `\|` |
| 线性段串联 | 3~4 行 `await` 独立调用 | `diet_linear_chain = r1 \| r2 \| r3 \| r4` 真正 LCEL |
| 对外接口 | 普通 async def | Runnable，ainvoke / abatch / callbacks 全支持 |
| LangSmith 接入 | 要在每个 LLM.invoke 里手写 tracer | 顶层 `with_config(callbacks=[...])` 一行搞定 |

## 四、改进 4：天气 API（高德）参与膳食决策 —— 完整前后端可落地方案

### 4.1 目标与设计原则

**业务目标**：
- 气温 > 30℃：推荐清凉消暑、凉拌、汤粥类菜品减少；优先冷食、水果、清淡食材；
- 气温 < 10℃：推荐暖身温补、炖煮、热汤、能量密度稍高的菜品；
- 降雨 / 湿度 > 80%：推荐祛湿食材（薏米、赤小豆、山药、冬瓜）；
- 强紫外线：推荐富含 VC / 番茄红素的抗氧化食材（番茄、橙子、西兰花）。

**工程原则**：
1. **不把天气 API Key 放前端**：前端只发"我要天气"请求，后端代理调用高德；
2. **可降级**：没 API Key / API 失败 → 自动跳过天气决策，不影响主流程；
3. **前端美观**：在 Welcome 区 / 对话气泡旁展示天气小卡片（温度+图标+饮食提示），不突兀；
4. **缓存**：同一地区 1 小时内不重复请求高德（免费账号有每日调用量限制）。

### 4.4 步骤 3：实现 weather_tool（LangChain @tool）

**新增文件** `backend/app/agent/tools/weather_tool.py`：

```python
"""
天气工具（高德地图 Web 服务 API）—— 给膳食建议加温度/气候语境

用途：
1. 被 Planner（改进1）识别为 need_weather=true 时显式调用；
2. 在 diet_plan 意图的 diet_linear_chain 中作为 r_fetch_weather 节点自动执行；
3. Function Calling（改进2）中由 llm_with_tools 自主调用。

输出（结构化 dict，既给 LLM 读也给前端展示）：
{
  "ok": true/false,
  "region": "杭州市",
  "city_adcode": "330100",
  "temperature": 28,            # 摄氏度
  "weather": "多云",            # 天气现象
  "wind_direction": "东南风",
  "wind_power": "3级",
  "humidity": "71",             # %
  "report_time": "2026-08-14 14:00:00",
  "diet_hints": [               # 确定性规则生成（不让 LLM 瞎想）
     "气温较高，建议多推荐凉拌、冷食、清炒菜品，减少厚重炖煮",
     "湿度偏高，可推荐薏米、赤小豆、冬瓜等祛湿食材"
  ],
  "fallback_reason": ""         # ok=false 时告诉 LLM / 前端为什么没拿到
}
"""
import logging
import json as _json
import time
from typing import Optional
from langchain_core.tools import tool

logger = logging.getLogger(__name__)

# 进程内内存缓存（同地区 1 小时内不重复请求）
# key: adcode|region_name, value: (expire_ts, result_dict)
_WEATHER_CACHE: dict = {}


def _gen_diet_hints(temperature: float, weather: str, humidity_pct: int) -> list[str]:
    """
    纯规则：根据气候参数生成膳食风格提示（直接喂给 LLM + 前端展示）。
    不依赖 LLM，100% 确定性。
    """
    hints = []
    # 温度
    if temperature >= 32:
        hints.append("气温炎热，推荐凉拌菜、冷食、凉面、清汤类菜品，减少重油重炖与火锅烧烤")
        hints.append("可增加清热消暑食材：绿豆、苦瓜、黄瓜、冬瓜、西瓜、荷叶、莲子")
    elif 28 <= temperature < 32:
        hints.append("气温较高，烹饪方式偏清淡，建议多用清炒、蒸、白灼，减少红烧油炸")
        hints.append("可推荐消暑汤品：绿豆汤、酸梅汤、银耳莲子羹")
    elif 18 <= temperature < 28:
        hints.append("气温舒适，烹饪方式可多样化，兼顾清爽与暖胃的搭配")
    elif 10 <= temperature < 18:
        hints.append("气温偏凉，推荐热汤、炖煮、煲仔类菜品，注意保证能量摄入")
        hints.append("可增加温补食材：羊肉、鸡肉、生姜、红枣、桂圆")
    else:
        hints.append("天气寒冷，优先推荐炖煮、红烧、煲汤类暖身菜品，可适当提高健康脂肪比例")
        hints.append("可推荐驱寒食材：生姜、大葱、蒜、胡椒、羊肉、牛肉、核桃")
    # 降雨/湿度
    wet_keywords = ("雨", "雷", "阵雨", "暴雨", "小雨", "中雨", "大雨")
    if any(k in weather for k in wet_keywords) or humidity_pct >= 80:
        hints.append("湿度高或有降雨，可推荐祛湿食材：薏米、赤小豆、山药、冬瓜、茯苓、白扁豆")
    # 强日晒
    if "晴" in weather and temperature >= 28:
        hints.append("紫外线较强，建议增加富含 VC 和番茄红素的抗氧化食材：番茄、橙子、西兰花、猕猴桃、蓝莓")
    return hints


@tool
async def weather_tool(
    region_name: Optional[str] = None,
    adcode: Optional[str] = None,
    user_id: Optional[int] = None,
) -> dict:
    """
    查询指定地区的实时天气，返回结构化气候参数 + 膳食建议提示。

    参数：
        region_name: 地区中文名（如"杭州"、"北京市"、"上海浦东新区"），
                     不传则从 user_id 对应的用户档案 region 字段自动取；
        adcode:      高德 6 位城市编码（优先级高于 region_name，能直接拿到就不查地理编码 API）；
        user_id:     用户 ID（如果 region_name 和 adcode 都不传，会调用 user_tool 查档案取地区）。

    返回：
        结构化天气 dict（见模块文档）。当 API Key 未配置/请求失败时 ok=false，
        fallback_reason 会说明原因，LLM 应据此跳过天气相关建议而不是报错。
    """
    from core.config_handler import get_settings
    settings = get_settings()
    cfg = settings.weather

    # --- 1) 开关 & Key 校验：未配置自动降级 ---
    if not cfg.enabled or not cfg.api_key or not cfg.api_key.strip():
        return {
            "ok": False,
            "region": region_name or "",
            "temperature": None,
            "weather": "",
            "humidity": "",
            "diet_hints": [],
            "fallback_reason": "天气功能未配置 API Key，已跳过天气适配"
        }

    # --- 2) 解析 region → adcode（如果只传了中文名） ---
    # 轻量级：只支持常见省会/地级市的硬编码映射表（省 1 次高德 geo API 调用；避免用户问"今天杭州吃什么"调 2 次 API）
    if not adcode and region_name:
        adcode = _adcode_lookup(region_name)

    if not adcode and user_id is not None:
        # 兜底：从用户档案取 region
        from agent.tools.user_tool import get_user_info
        prof = await get_user_info(user_id)
        if prof and prof.get("region"):
            adcode = _adcode_lookup(prof["region"])
            region_name = prof["region"]

    if not adcode:
        return {
            "ok": False,
            "region": region_name or "",
            "temperature": None,
            "weather": "",
            "humidity": "",
            "diet_hints": [],
            "fallback_reason": "未识别到有效地区，跳过天气适配（请在健康档案中填写地区，或在问题中明确城市名）"
        }

    # --- 3) 缓存命中 ---
    cache_key = f"{adcode}|{region_name or ''}"
    now = time.time()
    if cache_key in _WEATHER_CACHE:
        exp, cached = _WEATHER_CACHE[cache_key]
        if exp > now:
            cached["from_cache"] = True
            return cached

    # --- 4) 调用高德 API（使用项目已有的 httpx，不新增依赖） ---
    import httpx
    try:
        async with httpx.AsyncClient(timeout=cfg.timeout_seconds) as client:
            resp = await client.get(
                cfg.base_url,
                params={
                    "key": cfg.api_key.strip(),
                    "city": adcode,
                    "extensions": "base",   # "base"=实时天气(免费); "all"=预报(部分套餐收费)
                    "output": "JSON",
                },
            )
            resp.raise_for_status()
            data = resp.json()
    except Exception as e:
        logger.warning(f"[weather_tool] 高德 API 调用失败: {e}")
        return {
            "ok": False,
            "region": region_name or adcode,
            "temperature": None,
            "weather": "",
            "humidity": "",
            "diet_hints": [],
            "fallback_reason": f"天气服务暂时不可用({type(e).__name__})，已跳过天气适配"
        }

    # --- 5) 解析高德响应 ---
    try:
        if str(data.get("status")) != "1":
            raise ValueError(f"status={data.get('status')}, info={data.get('info')}")
        lives = data.get("lives") or []
        if not lives:
            raise ValueError("lives 数组为空")
        live = lives[0]
        temperature = float(live.get("temperature") or 0)
        humidity_pct = int(live.get("humidity") or 0)
        weather_str = live.get("weather") or ""
        result = {
            "ok": True,
            "from_cache": False,
            "region": live.get("city") or region_name or "",
            "city_adcode": live.get("adcode") or adcode,
            "province": live.get("province") or "",
            "temperature": temperature,
            "weather": weather_str,
            "wind_direction": live.get("winddirection") or "",
            "wind_power": live.get("windpower") or "",
            "humidity": live.get("humidity") or "",
            "report_time": live.get("reporttime") or "",
            "diet_hints": _gen_diet_hints(temperature, weather_str, humidity_pct),
            "fallback_reason": "",
        }
    except Exception as e:
        logger.warning(f"[weather_tool] 高德响应解析失败: {e}, raw={data}")
        return {
            "ok": False,
            "region": region_name or adcode,
            "temperature": None,
            "weather": "",
            "humidity": "",
            "diet_hints": [],
            "fallback_reason": f"天气数据解析异常({type(e).__name__})，已跳过天气适配"
        }

    # --- 6) 写缓存并返回 ---
    _WEATHER_CACHE[cache_key] = (now + cfg.cache_ttl_seconds, result)
    return result

    "郑州": "410100", "武汉": "420100", "长沙市": "430100", "长沙": "430100",

    "兰州": "620100", "西宁": "630100", "银川": "640100", "乌鲁木齐": "650100",
}


def _adcode_lookup(region_name: str) -> Optional[str]:
    """从中文名查 adcode。先精确匹配，再做前后缀模糊匹配（杭州 / 杭州市 / 杭州西湖区 → 都匹配 330100）"""
    if not region_name:
        return None
    region_name = region_name.strip()
    if region_name in _ADCODE_MAP:
        return _ADCODE_MAP[region_name]
    # 模糊：去"市/省/区/县"后缀
    for suf in ("市辖区", "特别行政区", "自治区", "省", "市", "区", "县"):
        if region_name.endswith(suf) and region_name[:-len(suf)] in _ADCODE_MAP:
            return _ADCODE_MAP[region_name[:-len(suf)]]
    # 模糊：取前缀 2~3 字匹配
    for k, v in _ADCODE_MAP.items():
        if region_name.startswith(k) or k.startswith(region_name):
            return v
    return None
```

```python
@router.get("/weather/current")
async def get_current_weather(
    region: str | None = None,
    user_id: int | None = None,
    current_user = Depends(get_current_user_safe),
):
    """
    前端调用：拿实时天气数据展示 UI 卡片。
    优先传 region（用户在对话里提到的城市），没传就用 current_user 的档案地区。
    响应直接透传 weather_tool 的结构化返回（ok/temperature/weather/diet_hints/...）。
    """
    from agent.tools.weather_tool import weather_tool
    rid = user_id or (current_user.user_id if current_user else None)
    return await weather_tool.ainvoke({
        "region_name": region,
        "user_id": rid,
    })
```
