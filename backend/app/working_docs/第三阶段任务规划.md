### 任务3.2：Agent 状态定义（高优先级）

**目标**：定义 LangGraph 全局状态 Schema

**文件路径**：`backend/app/agent/state.py`

**实现要点**：

```python
from typing import TypedDict, List, Optional, Annotated
import operator

class AgentState(TypedDict):
    """
    Agent 全局状态
    
    贯穿整个 Agent 执行流程，各节点共享此状态
    参考 LangGraph MessagesState 设计
    """
    
    # === 用户信息 ===
    user_id: str                                    # 用户ID
    user_profile: Optional[Dict]                    # 用户健康档案
    
    # === 对话上下文 ===
    messages: Annotated[List[Dict], operator.add]    # 对话历史（消息列表）
    session_id: str                                 # 会话ID
    
    # === Agent 中间产物 ===
    user_query: str                                 # 用户当前查询
    search_keywords: List[str]                       # 检索关键词
    retrieved_docs: List[Dict]                       # RAG 检索结果
    constraint_checks: List[Dict]                   # 忌口/慢病校验结果
    diet_plan: Optional[Dict]                       # 生成的膳食方案
    revise_count: int                               # 校验修正次数
    
    # === 控制流 ===
    current_node: str                               # 当前执行节点
    next_node: Optional[str]                        # 下一节点（条件分支）
    needs_info: bool                                # 是否需要补充信息
    final_response: str                             # 最终回复文本
```

**状态流转示意**：

```
用户发送消息
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  AgentState 初始化                                   │
│  user_query = "给我设计一份减脂餐"                    │
│  messages = [对话历史]                               │
│  revise_count = 0                                   │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
              各节点读写状态
              (详见任务3.4)
                       │
                       ▼
              final_response 生成
              返回给用户
```

**关键技术点**：
- 使用 `TypedDict` 定义类型安全的状态
- `Annotated[List, operator.add]` 实现消息列表自动追加
- 状态字段覆盖 Agent 执行全链路
- 支持从任意节点恢复执行

**测试验证**：
- 状态初始化测试
- 状态传递与更新测试
- 类型安全校验

```python
from langgraph.graph import StateGraph, END
from agent.state import AgentState
from agent.nodes.info_collect_node import info_collect_node
from agent.nodes.retrieve_node import retrieve_node
from agent.nodes.constraint_validate_node import constraint_validate_node
from agent.nodes.region_adapt_node import region_adapt_node
from agent.nodes.generate_node import generate_node
from agent.nodes.revise_node import revise_node

def build_agent_graph() -> StateGraph:
    """
    构建膳食搭配 Agent 状态图
    
    执行流程：
    1. info_collect → (信息充足?) → retrieve
    2. retrieve → constraint_validate → region_adapt → generate
    3. generate → revise → (校验通过?) → END
                            │               ↑
                            └── (需要修正) → generate
    """
    # 创建状态图
    workflow = StateGraph(AgentState)
    
    # 添加节点
    workflow.add_node("info_collect", info_collect_node)
    workflow.add_node("retrieve", retrieve_node)
    workflow.add_node("constraint_validate", constraint_validate_node)
    workflow.add_node("region_adapt", region_adapt_node)
    workflow.add_node("generate", generate_node)
    workflow.add_node("revise", revise_node)
    
    # 设置入口
    workflow.set_entry_point("info_collect")
    
    # 添加边
    workflow.add_edge("region_adapt", "generate")
    workflow.add_edge("generate", "revise")
    
    # 条件边：信息收集节点
    workflow.add_conditional_edges(
        "info_collect",
        lambda state: "needs_info" if state.get("needs_info") else "retrieve",
        {
            "needs_info": END,  # 追问用户后结束
            "retrieve": "retrieve"
        }
    )
    
    # 条件边：检索节点
    workflow.add_edge("retrieve", "constraint_validate")
    
    # 条件边：校验修正节点
    workflow.add_conditional_edges(
        "revise",
        lambda state: "regenerate" if _needs_revision(state) else "end",
        {
            "regenerate": "generate",
            "end": END
        }
    )
    
    # 编译图
    return workflow.compile()
```

## 五、关键设计思路

### 5.1 多步骤规划 Agent

```
传统 RAG 问答：
  用户提问 → 检索 → 生成 → 返回
  问题：忽略用户个体差异，生成食谱可能不合适

本项目 Agent：
  用户提问 → 信息收集 → 检索 → 校验 → 地域适配 → 生成 → 校验修正 → 返回
  优势：多步骤确保个性化，校验修正保证安全性
```

### 5.2 工具调用模式

```
Agent 节点执行流程：
┌─────────────────────────────────────────────────────────────┐
│  节点函数                                                    │
│  │                                                          │
│  ├── 1. 读取 AgentState（获取上下文）                        │
│  ├── 2. 调用工具函数（执行具体操作）                         │
│  ├── 3. 更新 AgentState（写入结果）                         │
│  └── 4. 返回 AgentState（传递给下一节点）                    │
│                                                              │
│  工具函数特点：                                              │
│  - 纯函数，输入→输出，无副作用                               │
│  - 独立测试，可单独验证                                     │
│  - 组合灵活，不同节点可复用相同工具                          │
└─────────────────────────────────────────────────────────────┘
```

## 六、技术选型理由

### 6.1 LangGraph vs LangChain Agent

| 对比项 | LangGraph | LangChain Agent |
|--------|-----------|-----------------|
| 可控性 | 高（显式状态图） | 低（自主决策） |
| 可调试性 | 高（每步可观测） | 低（黑盒） |
| 可靠性 | 高（固定流程） | 中（可能跳步） |
| 适用场景 | 流程固定的任务 | 开放式任务 |

**选择理由**：膳食搭配是**固定流程任务**（收集→检索→校验→生成），需要精确控制每一步，故选 LangGraph。

### 6.2 多 LLM 支持

| 提供商 | 优势 | 适用场景 |
|--------|------|---------|
| DeepSeek | 性价比高、中文好 | 日常使用（默认） |
| 通义千问 | 阿里生态、稳定 | 企业用户 |
| OpenAI | 通用能力强 | 高质量需求 |

### 6.3 Redis 用于对话记忆

| 对比项 | Redis | 数据库 |
|--------|-------|--------|
| 读写速度 | 微秒级 | 毫秒级 |
| TTL 支持 | 原生支持 | 需手动实现 |
| 适合场景 | 临时会话 | 长期存储 |

## 九、风险与应对

### 9.1 LLM 幻觉问题

**风险**：LLM 可能编造营养数据或推荐不合适食材

**应对**：
- Prompt 中明确禁止编造，要求基于知识库
- RAG 检索结果作为上下文注入
- 校验修正节点二次检查
- 输出结构化 JSON，便于程序校验

### 9.2 节点执行超时

**风险**：多节点串行执行耗时过长

**应对**：
- 每个节点设置超时阈值
- 关键节点（如 LLM 调用）使用流式输出
- 考虑并行化（检索+校验可并行）

### 9.3 状态图复杂度

**风险**：条件分支过多导致难以调试

**应对**：
- 每个节点保持单一职责
- 添加详细日志记录状态变化
- 使用 LangGraph 的可视化工具调试

### 9.4 Token 消耗过高

**风险**：多轮对话+长上下文导致 Token 超限

**应对**：
- 对话历史摘要压缩
- 检索结果限制条数
- Prompt 模板精简优化

## 十二、总结

- LangGraph 多步骤规划 Agent（区别于简单 RAG 问答）
- 5 个专业工具协同工作（信息/检索/校验/地域/营养）
- 自我校验修正机制（最多 3 次迭代，保证安全性）
- 多 LLM 抽象兼容（工程通用性）
- 对话记忆分层设计（短期+长期+摘要）

完成此阶段后，项目将具备完整的膳食搭配 AI Agent 能力，为第四阶段业务接口与前端开发打下核心基础。
