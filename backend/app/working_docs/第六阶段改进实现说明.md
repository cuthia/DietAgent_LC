# 第六阶段改进实现说明：LLM Dynamic Planning（动态规划层）

# 【1】LCEL 链实现

> 阶段：第六阶段 · 2026-08-14
> 对应改进方案：[docs/改进方案.md](../../docs/改进方案.md) 第一点
> 核心目标：把项目从"硬编码 6 步流水线 + 只会出食谱"升级为"LLM 动态规划 + 7 意图分支路由"的真 Agent

---

## 一、改进概述

### 1.1 改进前的痛点

旧版 `DietAgentChain.process()` 是固定的 6 步顺序 await：
```
信息收集 → 知识检索 → 约束构建 → 食谱生成 → 校验 → 输出
```

无论用户问什么（"我每天吃 4 个鸡蛋多不多？"、"算下 BMI"、"谢谢"、"一周减脂食谱"），都硬跑这 6 步：

- **答非所问**：用户问鸡蛋多不多，输出却是完整三餐食谱
- **成本浪费**：简单 QA 不需要 RAG + 8000 token JSON 生成
- **面试硬伤**：Planning 层完全硬编码，无法证明 LLM 动态决策能力

### 核心实现
1. Planner 是真 LCEL 链 ： PLANNER_PROMPT | self.llm | planner_parser ，初始化后类型为 RunnableSequence ，用 Pydantic BaseModel 描述 9 字段 ExecutionPlan schema

2. 7 意图分支路由 ：diet_plan（保留原 6 步）/ nutrition_qa / health_calc / food_eval / profile_update / casual_chat / info_collection

3. 7 个 @tool 工具齐全 ：覆盖 BMI/BMR/蛋白质计算、食材禁忌校验、档案更新（带白名单防注入）、RAG 检索、地域适配

4. 三层异常兜底 ：Planner 输出格式异常 → 降级 diet_plan；未知 intent → 降级 diet_plan；档案缺失 + 需个人数据意图 → 强制降级 info_collection

5. 流式接口同步改造 ：process_stream 加入 plan_execution 阶段事件 + 各分支的 start/complete 事件

### 1.2 改进后的架构

在 `step_collect_info` 之后、原 6 步流程之前，**插入 step_0 `step_plan_execution`**：让 LLM 作为 Planner 根据用户 Query + 用户档案 + 对话历史，输出结构化 `ExecutionPlan` JSON 决策，主流程据此分支路由：

| Intent | 用户 Query 示例 | 执行路径 |
|---|---|---|
| `diet_plan` | "一周减脂食谱" | 原 6 步流程（保留） |
| `nutrition_qa` | "每天吃 4 个鸡蛋多不多？" | 条件 RAG → QA LLM 直接答 |
| `health_calc` | "我 BMI 多少？" | bmi/bmr/protein 工具 → LLM 解释 |
| `food_eval` | "痛风能吃豆腐吗？" | 条件 RAG + food_taboo_check_tool → LLM 综合结论 |
| `profile_update` | "哦我海鲜过敏" | user_profile_update_tool 写库 → 确认回复 |
| `casual_chat` | "谢谢" | LLM 直接礼貌回复 |
| `info_collection` | 档案缺失 | step_format_output 输出追问 |

### 1.3 关键设计决策

1. **Planner 是真 LCEL 链**：`PLANNER_PROMPT | self.llm | planner_parser`，用 `JsonOutputParser(pydantic_object=ExecutionPlan)` 严格 schema 校验
2. **工具显式调用模式**：chain 根据 Planner 的 `tools_to_call` / `need_calc_tools` 等字段直接 `await tool.ainvoke(...)`，不用 bind_tools（这是第二点改进的内容，保持职责清晰）
3. **档案缺失强保护**：核心字段（age/gender/height/weight）缺失 + 需个人数据的意图（diet_plan/health_calc/food_eval）→ 强制降级 info_collection，防止 LLM 瞎算
4. **异常兜底降级**：Planner 输出格式异常或调用失败 → 自动降级为 diet_plan 意图，保持原流程不破坏
5. **diet_plan 意图保留原 6 步**：完整食谱 JSON 生成 + validate → revise 回路不变，向后兼容

| `protein_target_tool` | 同步 @tool | health_calc_tool.py | 蛋白质每日摄入目标（按膳食目标分级） |
| `food_taboo_check_tool` | 同步 @tool | validate_tool.py | 单食材禁忌校验（verdict: safe/warning/forbidden） |

| `rag_search_tool` | 异步 @tool | rag_tool.py | RAG 知识库检索（向量相似度 top_k） |
| `region_adapt_tool` | 同步 @tool | region_tool.py | 地域饮食文化特点查询 |

**工具化决策原则**：
- 纯数学/确定性逻辑（BMI/BMR/蛋白质）→ **必须工具化**（LLM 算数学会错、代不出公式）
- 写库操作（档案更新）→ **必须工具化**（加白名单防 Prompt 注入）
- 营养知识问答 → 不工具化，走 RAG + LLM 组织语言
- 完整食谱 JSON 生成 → 不工具化，仍走专用 `DIET_GENERATE_PROMPT`（5 层嵌套 JSON 用 function_call 不稳定）

## 四、Planner 决策 Schema（ExecutionPlan）

```python
class ExecutionPlan(BaseModel):
    intent: str               # 7 选 1：diet_plan/nutrition_qa/health_calc/food_eval/profile_update/casual_chat/info_collection
    plan_days: int            # 仅 diet_plan：1/2/3/5/7
    need_rag: bool            # 是否需要 RAG 检索
    rag_query_hint: str|None  # RAG 检索关键词建议
    need_weather: bool        # 是否需要天气决策（第四点改进用）
    need_calc_tools: list[str]# 健康计算器工具名列表
    profile_updates: dict|None# profile_update 意图的字段更新
    tools_to_call: list[str]  # 显式声明工具调用列表
    reasoning: str            # 决策推理过程（中文，用于日志/前端展示）
```

### Planner 异常兜底链

1. LLM 输出非 JSON / 缺 intent 字段 → 抛 ValueError → 降级 diet_plan
2. LLM 输出未知 intent → 警告 + 降级 diet_plan
3. LLM 漏字段 → `setdefault` 补默认值
4. 档案核心字段缺失 + 需个人数据意图 → 强制降级 info_collection
5. Planner 整体异常 → 降级 diet_plan + 记录 reasoning

### process() 改造后

```python
input_data = await self.step_collect_info(input_data)
input_data = await self.step_plan_execution(input_data)   # 新增 Planner

intent = input_data["plan"]["intent"]

if intent == "casual_chat":
    result = await self.step_casual_reply(input_data)
elif intent == "nutrition_qa":
    input_data = await self.step_retrieve_knowledge_conditional(input_data)
    result = await self.step_nutrition_qa_answer(input_data)
elif intent == "health_calc":
    input_data = await self.step_health_calc(input_data)
    result = await self.step_health_calc_explain(input_data)
elif intent == "food_eval":
    input_data = await self.step_retrieve_knowledge_conditional(input_data)
    input_data = await self.step_food_taboo_check(input_data)
    result = await self.step_food_eval_reply(input_data)
elif intent == "profile_update":
    input_data = await self.step_apply_profile_update(input_data)
    result = await self.step_profile_ack_reply(input_data)
elif intent == "info_collection":
    result = await self.step_format_output(input_data)
elif intent == "diet_plan":
    # 原 6 步剩余流程
    input_data = await self.step_retrieve_knowledge(input_data)
    input_data = await self.step_build_constraints(input_data)
    input_data = await self.step_generate_diet(input_data)
    input_data = await self.step_validate_diet(input_data)
    result = await self.step_format_output(input_data)

result["intent"] = intent   # 新增字段，前端可据此展示意图标签
```

## 八、面试讲解要点

### 8.1 "你的项目 Planning 层是硬编码的吗？"

> "改造后不是。我在主流程开始时插入了一个 LLM Planner 环节（step_0），它是一条真正的 LCEL 链 `PLANNER_PROMPT | LLM | JsonOutputParser`，让 LLM 根据用户 Query + 用户档案 + 对话历史，输出符合 Pydantic Schema 的结构化 ExecutionPlan JSON。主流程根据这个 plan 的 intent 字段做 7 路分支路由——这就是 Dynamic Planning。"

### 8.2 "为什么 diet_plan 意图保留原 6 步流程？"

> "因为完整食谱 JSON 是 5 层嵌套、7 天数组，字段约束极多（食材种类≥10、热量 3:4:2.5:0.5 分配、相邻天 60% 不重复）。这种复杂结构用 function_call 模式 LLM 经常漏字段，专用 `DIET_GENERATE_PROMPT` + System Prompt 强约束稳定性远高于 bind_tools。但其余 6 个意图（QA/计算/食材评估等）都用工具化方式处理。这是按场景做的工程取舍。"

### 8.3 "怎么防止 LLM 在档案缺失时瞎算 BMI？"

> "Planner 内置档案缺失强保护：核心字段（age/gender/height/weight）任一缺失 + 意图属于 {diet_plan, health_calc, food_eval}（需个人数据的意图）→ 强制降级为 info_collection 意图，优先追问完善档案。这层保护同时写在 Planner Prompt 的规则 7 和 chain 的 Python 兜底校验里，双重保险。"

### 8.4 "Planner 失败了怎么办？"

> "三层兜底：
> 1. LLM 输出格式异常 → 降级 diet_plan 意图（保持原 6 步流程不破坏）
> 2. intent 合法性校验 → 未知 intent 降级 diet_plan
> 3. 字段缺失 → setdefault 补默认值
> 整个 Planner 调用包在 try/except 里，任何异常都不会让主流程崩溃，最坏情况是退回到原来的硬编码 6 步行为。"

# 【2】LangChain Function Calling（bind_tools）标准 ReAct 闭环

> 对应改进方案：[docs/改进方案.md](../../docs/改进方案.md) 第二点
> 核心目标：把 nutrition_qa / health_calc / food_eval 三个分支从"chain 硬编码调工具"升级为"LLM 自主选工具 + 填参 + 基于观察生成结论"的标准 ReAct 模式

## 一、改进概述

### 改前 vs 改后

| 维度 | 【1】显式调用模式 | 【2】bind_tools ReAct 模式 |
|---|---|---|
| 谁决定调哪些工具 | chain 根据 Planner 的 `tools_to_call` 字段 | LLM 自主决定 |
| 谁填工具参数 | chain 从 user_profile 硬编码组装 | LLM 从档案上下文自主提取 |
| 工具执行结果如何用 | chain 把结果拼进 Prompt 再调 LLM | ToolMessage 追加回 messages，LLM 自主消化 |
| 标准 Agent 特征 | 不完整（无 Observation 闭环） | 完整 ReAct：Thought → Action → Observation → Conclusion |

### ReAct闭环流程
```
SystemMessage(档案+RAG+工具说明) + HumanMessage(用户问题)
  → LLM_WITH_TOOLS 第一轮：决定调哪些工具 + 填参数
  → _execute_tool_calls 并发执行 → ToolMessage[] 追加回 messages
  → LLM 第二轮：基于 Observation 生成最终结论（Markdown）
```


### 改造范围

- **新增**：`_execute_tool_calls`（并发工具执行器）+ `step_react_with_tools`（通用 ReAct 步骤）
- **改造**：nutrition_qa / health_calc / food_eval 三个分支改用 ReAct 模式
- **不动**：diet_plan（保留专用 Prompt）、casual_chat（无工具）、profile_update（确定性写库）

## 二、核心实现

### 2.1 bind_tools 注册（chain.py `__init__`）

```python
self.llm_with_tools = self.llm.bind_tools(list(self.tool_map.values()))
```

一行代码把 7 个 @tool 的 JSON Schema 注册给 LLM，LLM 调用时会返回 `tool_calls` 字段。

### 2.2 `_execute_tool_calls`：并发工具执行器

```python
async def _execute_tool_calls(self, ai_msg) -> List[ToolMessage]:
    # 1. 从 ai_msg.tool_calls 取出 LLM 决定调用的工具列表
    # 2. asyncio.gather 并发执行所有 tool_calls
    # 3. 同步工具用 invoke，异步工具用 ainvoke（_is_async_tool 自动识别）
    # 4. 工具异常不抛出，包装为 error 字符串（防止单个工具失败打断整条链）
    # 5. 返回 ToolMessage[]，喂回 LLM 形成 ReAct 闭环
```

```python
    # 1. 构造 messages：SystemMessage(含用户档案+RAG上下文+工具说明) + HumanMessage
    # 2. for i in range(max_iterations):
    #      ai_msg = await self.llm_with_tools.ainvoke(messages)
    #      if ai_msg 没有 tool_calls: 直接返回最终回答

    # 3. 达到 max_iterations 后，用不带 tools 的 LLM 生成最终回答
```

**设计要点**：
- `max_iterations=2`：默认 2 轮足够（第 1 轮调工具，第 2 轮写结论），防止死循环
- system_prompt 自动注入用户档案 + RAG 上下文，LLM 据此自主提取工具参数
- 三个分支复用同一个 `step_react_with_tools`，只传不同的 system_prompt

### 2.4 三分支改造

| 分支 | 改造前 | 改造后 |
|---|---|---|
| nutrition_qa | chain 拼 Prompt + LLM 直接答 | LLM 自主决定是否调 rag_search_tool 补充检索 |
| health_calc | chain 硬编码组装参数调 bmi/bmr → LLM 解释 | LLM 从档案自主提取参数 + 自主决定调哪些计算器 + 直接解读 |
| food_eval | chain 硬编码提取食材名调 food_taboo_check → LLM 综合 | LLM 自主识别食材 + 自主调 food_taboo_check_tool + rag_search_tool |

`step_health_calc_explain` 和 `step_food_taboo_check` 保留方法签名但变为透传（向后兼容 process 调用链）。

## 三、面试讲解要点

### "你的项目实现了标准 ReAct 吗？"

> "是的。在 nutrition_qa / health_calc / food_eval 三个分支中，我用 `self.llm.bind_tools(ALL_TOOLS)` 把 7 个 @tool 注册给 LLM，LLM 自主决定调哪些工具、填什么参数。工具执行结果通过 ToolMessage 追加回 messages 列表，LLM 基于 Observation 生成最终结论——这就是标准 ReAct 闭环：Thought → Action → Observation → Conclusion。"

### "为什么 diet_plan 不用 bind_tools？"

> "食谱 JSON 是 5 层嵌套、7 天数组，用 function_call 模式 LLM 经常漏字段。专用 Prompt + System Prompt 强约束稳定性远高于 bind_tools。但生成后的 validate → revise 校验回路仍然是工具化的 Observation 闭环。这是'对需要最强确定性的节点用专用 Chain，其余节点走标准 Agent ReAct'的工程取舍。"

### "ReAct 模式怎么防止死循环？"

> "`step_react_with_tools` 有 `max_iterations=2` 参数，默认 2 轮足够（第 1 轮调工具，第 2 轮写结论）。达到上限后会用不带 tools 的 LLM 强制生成最终回答。"

# 【3】混合 LCEL 编排（消除无用 import + 对外 Runnable 协议统一）

> 对应改进方案：[docs/改进方案.md](../../docs/改进方案.md) 第三点
> 核心目标：消除 `RunnableLambda / RunnablePassthrough` import 但不用的尴尬；线性段真正用 `|` 串成 LCEL 链；对外暴露标准 Runnable 接口

## 一、改进概述

### 改前 vs 改后

| 维度 | 改前 | 改后 |
|---|---|---|
| `RunnableLambda` import | 有，但全文件不用（面试扣分点） | 有，且每个 step 包成实例属性 + 线性段用 `\|` 串 |
| diet_plan 线性段 | 4 行 `await` 独立调用 | 1 行 `diet_linear_chain.ainvoke()` |
| 对外接口 | 普通 `async def process()` | `as_runnable()` 返回标准 Runnable（支持 abatch / callbacks / with_fallbacks） |

## 二、核心实现

### 3.1 每个 step 包成 RunnableLambda（chain.py `__init__`）

```python
self.r_collect_info      = RunnableLambda(self.step_collect_info)
self.r_plan_execution    = RunnableLambda(self.step_plan_execution)
self.r_retrieve          = RunnableLambda(self.step_retrieve_knowledge)
self.r_build_constraints = RunnableLambda(self.step_build_constraints)
self.r_generate_diet     = RunnableLambda(self.step_generate_diet)
self.r_validate_diet     = RunnableLambda(self.step_validate_diet)
self.r_format_output     = RunnableLambda(self.step_format_output)
```

### 3.2 线性段用 `|` 串成 LCEL sub-chain

```python
self.diet_linear_chain = (
    self.r_retrieve
    | self.r_build_constraints
    | self.r_generate_diet
    | self.r_validate_diet
)
```

process() 中 diet_plan 分支从 4 行 await 改为 1 行：
```python
input_data = await self.diet_linear_chain.ainvoke(input_data)
```

### 3.3 对外暴露 `as_runnable()`

```python
def as_runnable(self) -> RunnableLambda:
    async def _run(input_dict):
        return await self.process(user_id=input_dict["user_id"], user_query=input_dict["user_query"])
    return RunnableLambda(_run).with_config(run_name="DietAgentChain", tags=["DietAgent", "Production"])
```

支持的标准接口：
- `as_runnable().ainvoke({...})` — 异步调用
- `as_runnable().abatch([{...}, {...}])` — 批量处理
- `as_runnable().with_config(callbacks=[LangSmithTracer])` — 接入 LangSmith 链路追踪
- `as_runnable().with_fallbacks([fallback_runnable])` — 降级兜底

## 三、面试讲解要点

### "你的项目 RunnableLambda / RunnablePassthrough import 了但没用？"

> "改后用上了。每个 step 都包成 `RunnableLambda` 实例属性，diet_plan 的线性 4 连段（检索→约束→生成→校验）用 `|` 串成了 `diet_linear_chain`（类型 `RunnableSequence`），对外通过 `as_runnable()` 暴露标准 Runnable 接口。"

### "为什么不把整个流程都串成一条 LCEL 大链？"

> "因为我的流程有短路分支（信息不全要追问）和回路（校验失败要修正），用 `RunnableBranch` 嵌套写可读性差、调试堆栈不直观。所以采用混合策略：线性段用 LCEL `|`，分支/回路用 await 显式控制。但整体对外仍是标准 Runnable（`as_runnable()`），不破坏 LangChain 协议。"

# 【5】食谱修正闭环（diet_revise 意图 + 增量迭代）

> 第一改进点的延伸：把 Dynamic Planning 的意图空间从 7 扩展到 8，新增 `diet_revise` 意图
> 核心目标：用户对上一版食谱提意见后，AI 基于上一版做增量修改而非重新生成全新方案

## 一、改进前痛点

旧版只有 7 个意图，用户说"鸡蛋太多了换一下"会被 Planner 误判为 `diet_plan`，然后走完整的 6 步生成一份**全新**食谱，**用户的反馈意见完全丢失**，与上一版毫无关联——这是典型的"一次性出方案"，缺乏真正的对话迭代闭环。

## 二、整体架构

```
用户："鸡蛋太多了，早餐换燕麦"
            │
            ▼
┌─────────────────────────────────────────────────────┐
│ Planner (LLM 动态规划)                                │
│ • 识别意图 = diet_revise                              │
│ • revision_feedback = "鸡蛋太多；早餐换燕麦"           │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│ diet_revise_chain（LCEL 6 连段）                      │
│ retrieve → constraints → weather → fetch_prev_plan   │
│         → generate_diet → validate_diet              │
│                                                       │
│ step_fetch_prev_plan 关键步骤：                       │
│   MemoryManager.get_diet_history(limit=1)            │
│   ↓                                                   │
│   _summarize_prev_plan(prev)  # 精简避免 prompt 爆炸  │
│   ↓                                                   │
│   拼成 prev_diet_context 注入 prompt_input           │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────────────────┐
│ diet_prompt.py                                        │
│ 系统 prompt 第 8 条规则："修正模式 = 增量修改"         │
│ human 段新增 {prev_diet_context} 槽                   │
│   → LLM 看到上一版摘要 + 用户意见 → 输出修订版         │
└────────────────────┬────────────────────────────────┘
                     │
                     ▼
              新版食谱（plan_name 标 "v2/修订版"）
              agent_service.save_diet_plan() → 历史可被下一轮引用
```

## 三、关键改动点

### 3.1 Planner 层（planner_prompt.py）

- `ExecutionPlan` schema 新增 `revision_feedback: Optional[str]` 字段
- `intent` 枚举从 7 → 8：新增 `diet_revise`
- 系统规则新增第 2 条 `diet_revise` 识别规则：
  - 触发关键词：换一个/重新生成/改一下/不要/太多/太少/不喜欢/换成/去掉/太油腻/太清淡 等
  - 必须同时满足：对话历史最近一条 assistant 含食谱 + 当前 Query 在对该食谱提意见
  - 与 `casual_chat` 区别：用户说"谢谢这个食谱不错"是闲聊；"鸡蛋太多了换一下"才是修正
- 重要提醒新增约束：`revision_feedback` 非 `diet_revise` 意图必须为 `null`

### 3.2 Prompt 层（diet_prompt.py）

- 系统 prompt 严格规则新增第 8 条"修正模式"：
  - **基于上一版做增量修改**，不重新生成完全无关的方案
  - 用户满意的部分尽量保留，仅替换被意见指出的部分
  - 修改后总热量与营养结构波动 ≤ 10%
  - `plan_name` 标"v2/修订版"标识
- human 段新增第 7 个上下文槽 `{prev_diet_context}`，正常生成时填 "无"

### 3.3 Chain 层（chain.py）

**新增 step_fetch_prev_plan**：
- 仅 `diet_revise` 意图触发，其他意图直接透传
- 调用 `MemoryManager.get_diet_history(user_id, limit=1)` 取上一版保存的食谱
- 调用 `_summarize_prev_plan()` 把完整食谱精简成"方案名+总热量+前 3 天餐次摘要"短文本，避免 prompt token 爆炸
- 拼成 `prev_diet_context` 字符串注入 `prompt_input`

**新增 diet_revise_chain**（LCEL 6 连段）：
```python
self.diet_revise_chain = (
    self.r_retrieve
    | self.r_build_constraints
    | self.r_fetch_weather
    | self.r_fetch_prev_plan      # ← 比 diet_linear_chain 多这一段
    | self.r_generate_diet
    | self.r_validate_diet
)
```

**process() / process_stream()** 同步新增 `elif intent == "diet_revise":` 分支。

**降级保护**（重要！）：
- 取不到历史食谱 → 自动把 `intent` 改回 `diet_plan`，`revision_feedback` 清空
- 取历史异常 → 同上降级
- LLM 看 `prev_diet_context="无"` → 走正常生成（系统规则第 8 条自动失效）

### 3.4 配套微调

- `valid_intents` 集合新增 `diet_revise`
- `needs_profile_intents` 集合新增 `diet_revise`（档案缺失时也要先追问）
- `_intent_label()` 新增 `diet_revise → "修订食谱"` 中文标签
- `step_generate_diet` 的 `prompt_input` 新增 `prev_diet_context` 字段

依赖 [agent_service.py:122](file:///E:/Programs/Python%20Programs/DietAgent_LC/backend/app/services/agent_service.py#L122) 和 [agent_service.py:192](file:///E:/Programs/Python%20Programs/DietAgent_LC/backend/app/services/agent_service.py#L192) 已有的 `save_diet_plan` 调用——每次 `diet_plan` / `diet_revise` 成功生成后都会把新方案写入 `MemoryManager._user_diet_history`，下一轮 `diet_revise` 直接 `get_diet_history(limit=1)` 取最新一条即可。无需新增存储逻辑。

| 修改后营养结构偏差大 | `step_validate_diet` 环节会兜底修正（已有逻辑） |

## 七、面试话术要点

> "我意识到第一版只有 7 个意图，缺一个关键的反馈闭环——用户对食谱不满意提意见时，会被误判为重新生成全新方案，反馈意见丢失。
>
> 修复方法：在 Planner 的 ExecutionPlan schema 里加了 `diet_revise` 意图和 `revision_feedback` 字段；Chain 里加了 `step_fetch_prev_plan`，从 `MemoryManager.get_diet_history` 取上一版保存的食谱，精简后注入 `diet_prompt` 的 `prev_diet_context` 槽；系统 prompt 第 8 条规则强制 LLM 做增量修改而非重新生成，并且总热量波动不超过 10%。
>
> 关键设计点：
> 1）`_summarize_prev_plan` 把完整食谱 JSON 压缩成只含方案名+总热量+前 3 天餐次摘要的短文本，避免 prompt token 爆炸；
> 2）全链路降级：取不到历史 → 自动降级 `diet_plan`；取历史异常 → 同上；LLM 看 `prev_diet_context="无"` → 系统规则第 8 条自动失效，走正常生成；
> 3）流式版同步加了 `diet_revise` 进度事件，前端可见"正在取出上一版食谱并应用您的修改意见..."提示。
>
> 这样就形成了 '生成 → 用户反馈 → 增量修订 → 再保存 → 再反馈' 的真正对话式迭代闭环，而不是每次都从零开始。"
